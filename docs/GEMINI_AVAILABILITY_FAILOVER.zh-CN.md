# Gemini 可用性诊断与临时模型容灾设计

## 1. 背景与现场证据

2026-08-28 至 2026-08-29 的现场日志表明，用户能够正常访问 Google、Windows 系统代理与 v2rayN 进程也处于可用状态时，Gemini 天气识别仍会成批返回 HTTP `503 Service Unavailable`。同一时段并没有对应数量的 `429`，且稍后的真实请求可在数秒内成功，因此不能把全部失败归因于本地断网或代理关闭。

旧实现给整轮分析一个 60 秒共享预算，并在同一模型上最多重试三次。第一次调用可能等待四十多秒才得到 `503`，之后的退避与第二次调用耗尽剩余预算，最终元数据只留下 `Timeout`。这会同时造成两个问题：

1. 真实的服务端 `503` 被最后发生的取消覆盖，排障时误以为纯粹是本地网络超时；
2. 同一个 Gemini Flash 版本过载时，插件没有利用同一项目下其他可用 Flash 模型的机会。

## 2. 目标与非目标

本次实现的目标是：

- 保持每次天气在线分析最多 60 秒的总预算，不让重试阻塞后续安全检查；
- 对每个实际请求记录尝试序号、精确模型、HTTP 状态、失败分类和耗时；
- 主模型明确返回 `503` 时，在剩余预算足够的条件下临时尝试一个同系列 Flash 模型；
- 备用模型只短时接管，自动重新探测并回到用户配置的主模型；
- `429`、配额熔断与每日额度保持按模型独立，禁止通过轮换规避配额；
- 不改变“在线结果权威、本地结果仅作显式回退”的既有安全语义。

以下内容不属于本功能：

- 不做跨 API Key 轮换；
- 不承诺绕过 Gemini 免费层或付费层的项目级限制；
- 不把模型故障转移写回 `SelectedModel`；
- 不因网络异常、超时、认证错误、损坏 JSON 或 Schema 错误而盲目换模型；
- 不把本地启发式结果伪装成成功在线教师标签。

## 3. 状态机

```text
ConfiguredPrimary
    │ HTTP 503，且剩余预算 >= 5 秒
    ▼
TemporaryAlternate ── 成功 #1 ──> TemporaryAlternate
    │                                  │ 成功 #2
    │                                  ▼
    └──────── 主模型仍 503 <── ProbeConfiguredPrimary
                                       │ 成功
                                       ▼
                                ConfiguredPrimary
```

规则如下：

1. 正常情况下始终调用设置中选定的主模型。
2. 主模型返回明确 `503` 后，从 Gemini API 动态公布、支持 `generateContent` 的 Flash 系列模型中选择一个相近候选；排除图像生成、Live、音频、TTS 和嵌入模型。
3. 临时备用模型的首次成功（同一轮内接管）计为成功 #1；下一次在线检查继续由它承担，成功后计为 #2。
4. 再下一次在线检查探测原主模型。成功就立刻清除临时状态；仍为 `503` 则在同一预算内回到备用模型，并重新开始两次成功的短周期。
5. 整个状态只存在于 `GeminiAnalysisService` 实例内。断开/重连、安全监视器重建服务或用户主动换模型后自然回到配置主模型。
6. 计划性的“每 N 次调用一次”仍在模型状态机之前生效；只有实际在线检查才推进备用模型的成功计数。

## 4. 失败分类与诊断保真

`AnalysisProvenance.AttemptDiagnostics` 为每次传输保存以下非敏感字段：

- `attempt`：本轮尝试序号；
- `model`：实际请求的精确模型名；
- `httpStatus`：若收到 HTTP 响应则记录状态码；
- `failureCategory`：稳定、与提供方无关的失败分类；
- `durationMilliseconds`：该次传输耗时；
- `outcome`：`success`、`http_error`、`quota_rejected`、`network_error` 或 `timeout`。

这里不保存响应正文、API Key、图片、代理地址或相机凭据。最终错误选择遵循“具体服务端证据优先于后续预算取消”：如果前一次已收到 `503`，备用请求随后超时，最终分类仍为 `ServiceUnavailable`、HTTP 状态仍为 `503`，而超时保留在逐次诊断列表中。

如果一次失败之后剩余预算不足以覆盖退避时间和至少 5 秒的新请求窗口，插件不再发起注定被取消的重试，直接保留当前服务端失败。这避免把四十多秒后才返回的 `503`拖成表面上的整分钟超时。

## 5. 配额与安全边界

`429` 与结构化 `QuotaFailure` 不进入临时模型容灾：

- 收到配额失败的本轮只发送一次；
- 熔断键仍为 API Key 的 SHA-256 指纹加精确模型名；
- 短周期与每日配额继续遵循服务端重试时间和既有递增暂停；
- 插件不会因为某模型配额耗尽而主动寻找另一个模型继续消耗项目额度。

本功能只提高在线教师在服务端局部过载时的可用性。Safety Monitor 仍使用既有的在线权威、本地显式回退、数据新鲜度与失效安全规则；临时备用模型的成功结果会记录它自己的精确模型名，数据集后续可据此按教师版本筛选。

## 6. 回归验收

自动测试至少覆盖：

1. 主模型 `503`、备用模型 `200`，同一轮成功且逐次元数据同时保留两者；
2. 备用模型连续成功两次后，下一次请求回到主模型；
3. 三次 `503` 最终仍分类为 `ServiceUnavailable`，不会变成 `Unknown` 或通用超时；
4. 明确 `429` 只发送一次并打开配额熔断，不触发任何模型轮换；
5. Gemini 调用比例与配额暂停到期后的强制探测保持原行为。
