# AI Weather Advanced 本地云量小模型：数据审计、技术选型与训练路线

> 状态：设计基线；2026-08-29 依据当前 `dataset/v1` 只读审计结果整理。
> 目标：训练可以在高性能机器上完成，但最终模型必须在运行 N.I.N.A. 的远程台电脑上稳定、低资源、离线推理。
> 安全边界：本地模型首先只做影子推理和可行性验证；在获得足够跨夜、人工复核证据前，不单独承担开顶安全判断。

## 1. 结论

现在**可以开始训练第一个可行性验证模型**，但还不能把它称为可替代 Gemini 的生产模型。

最合理的路线不是 YOLO-World，也不是直接把 SAM 塞进插件，而是：

1. 继续用成功的在线 Gemini 结果作为**标签教师**，人工复核关键样本；
2. 在高性能训练机上用 DINOv3 等较强视觉基础模型作为**特征教师/对照基线**；
3. 训练一个面向整幅全天相机画面的多任务模型，直接预测云量、天气类别及质量/不确定性；
4. 将知识蒸馏到 MobileNetV3-Large 或同级轻量 CNN 学生；
5. 导出 ONNX，在本台 Ryzen 7 PRO 5850U 上运行；先 FP32 验证精度，再以静态 INT8 量化做可选优化；
6. 让安全阈值、迟滞、失联过期和最终 `Safe/Unsafe` 规则继续留在插件的确定性代码中，而不是交给神经网络自由决定。

一句话架构：

```text
在线 Gemini（标签教师） + DINOv3/公开数据（训练期特征与先验）
                           ↓
               轻量多任务学生模型
                           ↓
                  ONNX Runtime / CPU
                           ↓
        云量、类别、置信度 → 插件确定性安全状态机
```

### 2.3 是否已经“够训练”

需要区分三个问题：

- **能否训练出会收敛的模型：**可以；
- **能否比较两三种架构并完成 ONNX 部署：**可以；
- **能否证明模型足够可靠，可以控制远程屋顶：**不可以。

275 张足够做 Phase A 的管线实验。由于相邻帧高度相关，不能把“图片数量”直接当成“独立天气场景数量”。生产验证应按夜晚和天气事件计数。

## 3. 为什么不优先选择 YOLO-World

[YOLO-World](https://arxiv.org/abs/2401.17270) 的核心任务是开放词汇目标检测：把具有相对明确边界的对象用框或实例区域定位，并通过图文预训练扩展可检测类别。

全天相机的云量判断与此并不匹配：

- 云是连续、半透明、边缘模糊且可能覆盖整个视野的介质，不是天然的独立目标实例；
- 我们的主要输出是整幅天空的覆盖百分比和安全相关类别，而不是“这里有几个云对象”；
- 框标注会把框内晴空一起算入，不能自然表达透明星云、薄云和光污染；
- 开放词汇能力对固定的 `Clear/PartlyCloudy/MostlyCloudy/Overcast/Foggy/Rainy` 输出没有明显收益；
- 检测头、NMS 和文字编码器会增加部署复杂度，却不直接改善云量回归。

因此 YOLO-World 可以作为研究对照，但不应成为第一版学生模型。

## 4. 为什么暂时不把 SAM 当作主模型

[Segment Anything](https://arxiv.org/abs/2304.02643) 是可提示的通用分割基础模型，擅长根据点、框或掩码提示产生高质量的、类别无关的区域掩码。它不会天然知道哪个掩码是云，也不会自动把半透明云边界变成适合本站安全判断的云量真值。

目前直接使用 SAM 会遇到：

- 我们没有云/晴空像素级真值；
- 自动掩码是类别无关的，可能优先分出建筑、圆顶边缘、水滴、灯光和时间水印；
- 夜间薄云与背景的边界本来就不唯一；
- SAM 级编码器不适合常驻这台 N.I.N.A. 电脑；
- 为 275 张图追求精细像素边界，成本高于它对最终安全状态的实际收益。

SAM 的合理位置是**后续标注工具**：当积累了一批人工确认的代表性图片后，用 SAM/DINO 稠密特征辅助生成初始掩码，再由人修正。分割可作为辅助任务，不是 Phase A 的前置条件。

## 5. 推荐任务定义：不是“混沌训练”，而是结构化端到端多任务学习

第一版不必标出每一片云的位置。整图经过网络后直接输出数值完全可行，但训练目标必须结构化。

### 5.1 输入

- 从 1920×1080 保存图生成 384×216 或 512×288 的训练输入；
- 保持 16:9，不拉伸全天相机圆形视野；
- 使用固定有效天空 ROI/掩码，降低屋檐、圆顶边缘和时间水印的影响；
- 归一化参数、RGB 顺序和 resize 算法必须与 C# 推理实现完全一致；
- 太阳高度、月亮高度/月相可作为少量结构化输入，但 Phase A 必须同时做“纯图像”对照，防止模型只记住天文条件。

### 5.2 输出头

推荐一个共享视觉骨干，连接多个轻量输出头：

1. **云量回归：**0–100%，主损失使用 Huber/Smooth-L1；
2. **云量区间的序数分类：**例如 0–10、10–30、30–50、50–70、70–90、90–100，用于稳定阈值附近的学习；
3. **天气类别：**Clear、PartlyCloudy、MostlyCloudy、Overcast；
4. **雨/雾：**暂时只做辅助头或保持 `unknown`，在正样本充足前不能授权其报告“未检测到”；
5. **图像有效性/OOD：**遮挡、过曝、冻结、解码损坏或明显不属于本站相机分布；
6. **不确定性：**通过深度集成、MC dropout、温度校准或分位数回归之一得到可用于拒绝预测的信号。

最终 `Safe/Unsafe` 不作为唯一训练标签。只训练二分类安全结果会丢失云量连续信息，并容易学到当前阈值的偶然规则。插件应继续用云量、雨雾、置信度、数据新鲜度和迟滞阈值计算最终状态。

## 6. 教师与学生的分工

这里存在两类“教师”，需要明确区分：

### 6.1 标签教师：Gemini

Gemini 当前给出天气类别、云量、雨雾和文字解释，是现有 275 个伪标签的来源。它的优点是已经适应本台相机画面；缺点是模型版本变化、API 波动和系统偏差会进入标签。

处理原则：

- 保留模型名、提示词版本、HTTP 状态、延迟和天文上下文；
- 同一图片重复调用产生冲突时，不把某一次结果自动视为绝对真值；
- 人工接受/修正标签的权重高于仅教师标签；
- 不使用本地启发式结果作为监督真值；
- 不把 Gemini 的 `Safe/Unsafe` 直接蒸馏成屋顶控制权。

### 6.2 特征教师：DINOv3 或其他强视觉基础模型

[DINOv3](https://ai.meta.com/research/dinov3/) 是自监督视觉基础模型，强调高质量全局与稠密特征，并提供不同尺寸及面向受限设备的 ConvNeXt 变体。它适合在训练机上做：

- 冻结骨干 + 轻量回归/分类头基线；
- 生成全局和 patch 特征，帮助小数据场景；
- 与 Gemini 标签共同训练较强教师；
- 将 logits、连续云量和中间特征蒸馏给轻量学生。

DINOv3 不需要部署到 N.I.N.A. 电脑。发布任何基于特定预训练权重的派生模型前，必须重新核对对应 checkpoint 的许可证与再分发条款。

[知识蒸馏](https://arxiv.org/abs/1503.02531) 的目标正是把大型模型或集成模型的知识压缩进较容易部署的小模型，这与“高性能机器训练、低功耗台站推理”的约束一致。

## 7. 推荐学生模型

### 首选：MobileNetV3-Large，多任务头

[MobileNetV3](https://arxiv.org/abs/1905.02244) 面向移动/CPU 延迟设计，结构成熟、ONNX 支持好，并有可用于轻量语义分割的 LR-ASPP 设计。它适合作为第一版，因为：

- 模型规模和 CPU 延迟容易控制；
- CNN 对 275 张的小数据微调通常比从零训练 ViT 更稳；
- 全局池化后连接回归和分类头很直接；
- 后续需要粗分割时，可以增加轻量 decoder；
- Windows x64 ONNX Runtime 部署风险低。

建议同时训练以下对照：

- MobileNetV3-Small：速度/体积下界；
- MobileNetV3-Large：推荐主线；
- EfficientNet-B0 或 RepViT-M0/M1：精度对照；
- 冻结 DINOv3-S/ConvNeXt-T + 线性头：训练期上界，不作为首个部署候选。

不要一开始就同时引入分割、大型 ViT、时间序列网络和复杂气象特征。先用最小可解释基线确定数据是否包含足够信号。

## 8. 数据划分与防泄漏

绝对禁止对 275 张连续帧做普通随机 80/10/10。那会把同一片云在几分钟内的相邻画面分到训练和测试中，得到虚假的高分。

必须采用：

```text
日期/夜晚
  └─ 连续天气事件
       └─ 感知哈希近重复簇
            └─ 样本
```

同一近重复簇和同一连续天气事件只能进入一个 split。当前只有 6 个 UTC 日期，勉强可以做 4 夜训练、1 夜验证、1 夜测试，但结果方差会很大。更合适的工程目标是：

- 管线验证：当前 6 夜即可；
- 初步泛化评估：至少 12–20 个独立夜晚；
- 进入长期影子运行：覆盖不同月相、透明度、湿度、云速与相机状态；
- 季节可靠性：跨季节持续收集，保留从未参与调参的封存测试夜。

所有雨、雾、镜头结露、遮挡、极亮月光、局部强光、RTSP 花屏/冻结等稀有样本必须按事件成组，不能切散。

## 9. 公开数据集能做什么，不能做什么

### SWINySEG / SWIMSEG / SWINSEG

[SWINySEG](https://www.vintage.winklerbros.net/swinyseg.html) 含 6768 个昼夜天空/云 patch 及二值掩码，来自校准的地基全天成像设备，并由气象专家参与标注。它是最接近夜间分割预训练的公开资源之一。

用途：

- 学习基础云纹理和粗分割；
- 预训练轻量分割辅助头；
- 验证网络是否具备云/晴空区分能力。

限制：

- 新加坡气候、设备、色彩响应和本站不同；
- patch 与本站完整 16:9 全天画面构图不同；
- 不能替代本站的最终测试集。

### CCSN / CloudNet

[CCSN](https://github.com/upuil/CCSN-Database) 含 2543 张、11 个气象云属类别的地基云图；对应的 [CloudNet 论文](https://agupubs.onlinelibrary.wiley.com/doi/full/10.1029/2018GL077787) 研究的是云类型分类。

用途：增强云纹理表征、辅助预训练天气类别；限制是它不提供本站需要的全天覆盖百分比，也不是夜间安全监控数据。

### 使用原则

公开数据只进入预训练或辅助任务。验证集和测试集必须来自本站、按夜隔离、经过人工复核；否则公开数据上的高分不能证明屋顶安全。

## 10. 人工复核优先级

不需要先把 275 张全部逐张精修。第一轮采用分层抽样：

1. 每个云量区间、每个日期各抽若干张；
2. 40% 与 50% 阈值上下的样本优先；
3. 全部 2 张雨和 10 张雾必须人工检查；
4. 所有 68 张近重复标记至少检查簇代表图；
5. 教师与旧学生差值最大的样本优先；
6. 极亮月光、镜头反光、边缘遮挡和水滴优先；
7. 对“模型很自信但人不确定”的图允许标为 `ambiguous`，不要强行给精确百分比。

建议人工标签同时保存：

- 云量点估计；
- 可接受区间，例如 35–45%；
- 类别；
- 是否雨/雾/镜头水滴；
- 图像是否有效；
- 备注与复核者置信度。

区间标签可以用区间损失训练，避免把视觉上不可精确到 1% 的判断伪装成绝对真值。

## 11. 训练阶段

### Phase A：管线可行性

- 从当前 275 张生成按夜/事件分组的数据索引；
- 训练 MobileNetV3-Large 的云量回归 + 区间分类 + 四类天气头；
- 对比只用 ImageNet 初始化和冻结 DINOv3 特征两条基线；
- 完成 PyTorch → ONNX → C# 一致性测试；
- 输出模型卡、归一化参数、输入尺寸、opset 和类别顺序。

此阶段只回答：“模型是否能学到本站夜空信号、导出后是否一致”。

### Phase B：教师增强与蒸馏

- 用人工复核样本校准 Gemini 标签；
- 使用强特征教师训练较高精度模型；
- 将软云量分布、类别 logits 和可选中间特征蒸馏给 MobileNetV3；
- 对相邻帧使用一致性正则，但不能让它们跨 split；
- 建立 OOD/无效图拒绝机制。

### Phase C：插件影子推理

- 在线 Gemini 仍是权威结果；
- 本地 ONNX 对每次同一帧同时推理，只记录差值，不影响安全状态；
- 标签检查器显示在线、本地、人工结果和误差；
- 连续运行至少 30 个有效夜晚，统计模型在真实代理中断、月光、薄云和坏帧下的行为。

### Phase D：受限回退

只有通过验收后，才允许在线失败时采用本地 ONNX。仍必须满足：

- 不确定或 OOD → `Unknown/Unsafe`；
- 模型超时/加载失败 → `Unknown/Unsafe`；
- 雨雾头证据不足时不能据此恢复安全；
- 安全状态机继续执行迟滞、过期和外部传感器 AND 规则；
- 保留一键退回旧启发式或完全禁用本地模型的能力。

## 12. ONNX 部署约束

目标电脑：

- AMD Ryzen 7 PRO 5850U，8 核 16 线程；
- 约 12 GiB RAM；
- AMD 集成显卡，但首版不得依赖特定 GPU 驱动或 DirectML；
- N.I.N.A.、RTSP、设备驱动和可能的 OBS 同时运行。

首版部署预算：

| 指标 | 目标 |
|---|---:|
| 推理后端 | ONNX Runtime CPU |
| 输入 | 384×216 或 512×288 RGB |
| 模型文件 | FP32 ≤ 30 MiB；INT8 目标 ≤ 10 MiB |
| 单次 p95 总耗时 | ≤ 1 秒，包含 Bitmap 预处理 |
| 额外常驻内存 | ≤ 300 MiB |
| 并发 | 单实例、串行推理 |
| GPU | 非必需 |
| 网络 | 非必需 |

[ONNX Runtime 官方量化指南](https://onnxruntime.ai/docs/how-to/quantization.html) 建议 CNN 优先尝试静态量化，并用校准数据预先确定激活范围。实际流程应是：

1. 先发布 FP32 模型并验证 PyTorch/ONNX 输出一致；
2. 使用按夜、云量和月相分层的校准集做静态 INT8 QDQ；
3. 比较 FP32 与 INT8 在封存夜测试集上的云量误差和安全阈值混淆；
4. 只有精度损失可接受且本机实测更快，才默认使用 INT8；
5. 不假设量化一定提速，必须以 5850U 实测为准。

建议 ONNX opset 使用插件所带 Runtime 能稳定支持的保守版本，并在发布包中锁定 Runtime、模型格式版本、输入布局和归一化元数据。

## 13. 验收指标

不能只看训练损失或随机图片准确率。至少报告：

- 云量 MAE、RMSE、90/95 分位绝对误差；
- 40%/50% 两个安全阈值附近的混淆矩阵；
- Unsafe recall，特别是模型错误报告 Safe 的次数；
- 每个独立夜晚的指标，而不只是全体平均；
- 晴、局部多云、大部多云、阴天的 macro-F1；
- 校准误差与拒绝率；
- OOD、遮挡、冻结、解码损坏的拒绝率；
- 本机 FP32/INT8 p50、p95 延迟和峰值内存。

Phase A 的建议目标是云量 MAE ≤ 15 个百分点，主要用于确认方向。进入受限回退前，建议在人审封存集上达到：

- 云量 MAE ≤ 10 个百分点；
- 90 分位绝对误差 ≤ 20 个百分点；
- 40%/50% 阈值附近有专门测试集；
- 严重多云、阴天、雨雾的已观察错误安全报告为 0；
- 至少 30 个影子运行夜没有模型加载、内存增长或长尾卡顿；
- 任何不确定性超限样本都拒绝恢复为 Safe。

这些是工程准入门槛，不是数学上的永久安全保证。样本量必须与“0 次错误”的置信区间一起报告。

## 14. 下一步执行清单

1. 从当前标签生成按日期、事件和感知哈希簇分组的只读训练索引；
2. 在标签检查器完成第一批分层人工复核，尤其是阈值附近与全部雨雾样本；
3. 建立 MobileNetV3-Large 多任务 baseline；
4. 建立冻结 DINOv3 特征 + 轻量头的训练期上界；
5. 采用 group split，并输出逐夜指标；
6. 导出 FP32 ONNX，编写 PyTorch/ONNX 数值一致性测试；
7. 在本机测量预处理、推理、内存和长时间稳定性；
8. 再决定是否加入轻量分割头、知识蒸馏和 INT8；
9. 插件只先加入“影子模型”模式，不改变现有在线权威安全结果；
10. 数据和证据达到门槛后，再讨论把 ONNX 提升为在线失败时的受限回退。
